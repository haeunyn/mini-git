# 알고리즘 설명 — 이 프로젝트가 쓰는 5가지

## 1. 커밋 그래프는 왜 DAG 인가

**DAG** = Directed Acyclic Graph, 방향성 비순환 그래프.

| 성질 | 왜 그런가 |
|---|---|
| **방향성** Directed | 커밋은 "내 부모가 누구인지"만 안다. 부모는 자식을 모른다. 시간이 한 방향으로만 흐르기 때문이다. |
| **비순환** Acyclic | 사이클이 생기려면 "내 조상이 내 자손"이어야 하는데, 커밋을 만들 때는 **이미 존재하는 커밋만** 부모로 삼을 수 있다. 아직 없는 커밋을 부모로 지정할 방법이 없으므로 원리상 불가능하다. |
| **트리가 아닌 이유** | merge 커밋은 부모가 **2개**다. 트리는 부모가 1개여야 한다. |

> 이 성질이 중요한 이유: 사이클이 없다는 보장이 있어야 **위상 정렬이 가능**하다.
> 사이클이 있으면 "누가 먼저인지" 정할 수 없는 커밋이 생긴다.

## 2. LOG — 위상 정렬 (칸 알고리즘)

**왜 최신순이 아닌가:** 브랜치가 갈라지면 시간순과 조상관계가 어긋난다.
feature 에서 9시 15분에 커밋하고 main 으로 돌아가 9시 30분에 커밋하면,
둘은 서로 조상이 아니다. 시간만으로 줄 세우면 "부모보다 자식이 먼저" 나올 수 있다.

**칸(Kahn) 알고리즘**

```
1. 각 커밋의 '남은 부모 수'(진입 차수)를 센다
2. 부모가 0개인 커밋을 대기줄에 넣는다
3. 하나 꺼내 출력 → 그 자식들의 '남은 부모 수'를 1씩 줄인다
4. 0이 된 자식을 대기줄에 넣는다 → 2번으로
```

시간복잡도 **O(V + E)** — 커밋과 간선을 한 번씩만 본다.

> 동률일 때 `(timestamp, hash)` 로 정렬해 둔다. 결과가 매번 같아야 테스트할 수 있기 때문이다.

## 3. PATH — BFS 최단 경로 + 사전순 최소

**정의:** 커밋-부모 연결을 **무방향 간선**으로 보았을 때 간선 수가 최소인 경로.
무방향으로 보는 이유는, 조상 방향으로만 가면 **형제 커밋 사이에 길이 없기** 때문이다.
양방향이면 공통 조상을 거쳐 돌아갈 수 있다.

**왜 BFS 인가:** BFS 는 가까운 곳부터 층층이 퍼지므로, 어떤 노드에 **처음 도달한
순간이 곧 최단 거리**다. DFS 는 깊이 먼저 파고들어 먼 길로 먼저 도착할 수 있다.

**사전순 최소를 보장하는 방법 — 2단계**

```
1) target 에서 BFS → 모든 커밋의 'target 까지 거리'를 구한다
2) source 에서 출발해, 거리가 정확히 1씩 줄어드는 이웃 중
   해시가 가장 작은 것을 고르며 따라간다
```

**왜 욕심쟁이 선택이 전체 최소가 되는가:** 최단 경로들은 길이가 모두 같고,
커밋 해시는 **전부 6자리로 길이가 같다.** 그러면 문자열 비교가 앞에서부터
한 칸씩 비교하는 것과 같아지므로, 매 단계 최소를 고르면 전체가 최소가 된다.

> 해시 길이를 6자로 고정한 것이 이 성질을 위한 설계였다. 길이가 들쭉날쭉하면
> `"9a"` 와 `"10abc"` 비교처럼 직관과 어긋나는 결과가 나온다.

## 4. ANCESTORS — BFS 조상 탐색

부모 방향으로만 BFS 를 돈다. **O(V + E)**.

`visited` 집합이 꼭 필요하다. merge 커밋이 있으면 **같은 조상에 두 갈래로
도달**할 수 있어서, 표시해 두지 않으면 같은 커밋을 여러 번 방문한다.

## 5. 역색인 (Inverted Index)

**'역(inverted)'인 이유**

```
정방향:  커밋 → 그 커밋의 단어들
역방향:  단어 → 그 단어가 들어 있는 커밋들   ← 이쪽
```

**시간복잡도 비교** — 커밋 N개, 메시지 평균 길이 L, 결과 K개

| 방식 | 복잡도 | 커밋 1만 개에서 "login" 찾기 |
|---|---|---|
| 순회 검색 | O(N × L) | 1만 개 메시지를 전부 읽는다 |
| **역색인** | **O(1) + O(K)** | 해당 3개만 바로 꺼낸다 |

**대가:** 커밋할 때 인덱스를 갱신하는 비용과 메모리를 더 쓴다.
검색이 잦고 쓰기가 드물면 이득이다 — 모든 검색 엔진이 이 구조다.

인덱스는 2종이다: `keyword -> [hash]`, `author -> [hash]`

## 6. 정렬 — 직접 구현 (표준 API 금지)

| | 평균 | 최악 | 추가 메모리 | 안정? |
|---|---|---|---|---|
| **병합 정렬** merge sort | O(n log n) | O(n log n) | O(n) | ✅ |
| **삽입 정렬** insertion sort | O(n²) | O(n²) | O(1) | ✅ |

**안정 정렬(stable)이란** 정렬 기준이 같은 두 항목의 **원래 순서가 뒤바뀌지 않는 것**.
작성자 기준으로 정렬할 때 같은 작성자의 커밋이 커밋 순서를 유지해야 읽기 편하다.

구현에서 안정성을 지킨 방법:
- 병합 정렬: 합칠 때 `<=` 가 아니라 **"오른쪽이 더 작을 때만"** 오른쪽을 가져온다
- 삽입 정렬: **"왼쪽이 더 클 때만"** 민다 (같으면 멈춘다)

**실측 결과** (`./run.sh bench`)

```
무작위 입력          크기 4000 → 병합 7.8ms / 삽입 331.8ms  (42.6배 차이)
이미 정렬된 입력      크기 4000 → 병합 5.6ms / 삽입   0.5ms  (삽입이 10배 빠름)
```

> **최악 복잡도만 보고 고르면 안 된다**는 좋은 예다. 삽입 정렬은 이미 정렬된
> 입력에서 밀 일이 없어 O(n)에 가까워진다. 실제 파이썬의 Timsort 도
> "거의 정렬된 구간"을 찾아 삽입 정렬을 섞어 쓴다.
